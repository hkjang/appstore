RELEASE RUNBOOK

태그, image, archive와 화면 version을 하나로 맞추기

안정 SemVer Git tag를 유일한 release version으로 사용합니다. Workflow는 동일 version을 Go binary, OCI label, Docker tag와 archive 이름에 주입하고 실제 offline smoke test 후에만 게시합니다.

목차명명 계약릴리스 Gate화면 캡처로컬 검증커밋·태그자동 Workflow게시 후 검증Pages

현재 단일 archive 계약은 Linux/AMD64를 대상으로 합니다. ARM64가 필요하면 같은 이름을 덮어쓰지 말고 먼저 architecture별 명명 정책을 승인받습니다.

2. 릴리스 Gate

  • Go unit·handler·OIDC·RBAC·Key·Workflow·AI streaming·MCP test 통과
  • React strict typecheck, lint, component·route·authorization·stream test 통과
  • Playwright desktop·mobile 핵심 route와 refresh test 통과
  • Frontend production bundle의 Google Fonts, CDN, Unsplash 참조 0건
  • 애플리케이션 env 접근이 승인된 네 이름과 정확히 일치
  • Docker image가 non-root이고 read-only filesystem에서 ready
  • 내부 전용 Docker network에서 PostgreSQL만 연결한 smoke test 통과
  • 사용자·관리자·운영 가이드와 screenshot manifest 검증 통과
금지: 빌드 성공만으로 tag를 만들지 않습니다. public, SSO, Admin, Key rotation, Workflow OFF/ON, streaming cancel과 route refresh를 화면에서 확인해야 합니다.

3. 전체 페이지 캡처 갱신

docs/assets/screenshots/manifest.json은 v2.1.2의 모든 React route에 대한 desktop·mobile 전체 페이지 WebP, 대체 텍스트, pixel 크기, 상태, 버전과 SHA-256을 기록합니다. 캡처는 Playwright의 deterministic fixture를 사용하며 make screenshots VERSION=v2.1.2으로 재현합니다.

  1. 실제 사용자·Secret이 없는 demo seed와 고정 시각을 사용합니다.
  2. 로그인, submit, 개인 영역, review와 모든 admin route에 필요한 권한 세션을 준비합니다.
  3. 각 항목을 fullPage: true로 캡처해 PNG 원본을 만듭니다.
  4. make screenshots VERSION=v2.1.2으로 WebP를 게시하고 manifest의 status, version, 크기와 checksum을 갱신합니다.
  5. OIDC·AI Secret, Key 원문, 실제 email, 실제 내부 hostname과 Request body가 보이지 않는지 검수합니다.
  6. 홍보 gallery에는 대표 화면, 사용자·관리자 가이드에는 해당 업무 화면을 배치합니다.

v2.1.2 manifest의 82개 항목은 모두 captured 상태이며 실제 WebP와 SHA-256이 일치해야 문서 검사를 통과합니다.

4. 로컬 release archive 검증

make test
make check
make test-e2e
make archive VERSION=v2.1.2
make verify-archive VERSION=v2.1.2
./scripts/smoke-image.sh appstore:v2.1.2

scripts/release-image.sh는 tag 형식을 검사하고 image를 build한 뒤 gzip -9n으로 저장합니다. 검증 script는 Docker manifest의 RepoTag, OCI version label과 non-root user를 확인하고 archive를 다시 load합니다.

5. 최종 커밋, push와 tag

  1. 작업 트리를 검토합니다.
    git status --short와 diff에서 secret, generated cache, 원격 runtime asset과 관계없는 사용자 변경이 섞이지 않았는지 확인합니다.
  2. 최종 commit을 만듭니다.
    코드, migration, 문서와 실제 screenshot manifest가 같은 release 상태를 설명해야 합니다.
  3. main에 push합니다.
    CI와 Pages workflow가 성공할 때까지 tag를 만들지 않습니다.
  4. annotated tag를 만들고 push합니다.
    git tag -a v2.1.2 -m "AppStore v2.1.2"
git push origin main
git push origin v2.1.2

Release workflow는 tag commit이 origin/main의 ancestor가 아니면 중단합니다. 이미 존재하는 GitHub Release를 덮어쓰지 않습니다.

6. GitHub Release 자동화

.github/workflows/release.yml은 v*.*.* tag push에서 실행되며 내부 정규식은 안정 SemVer만 허용합니다.

  1. Go·React test와 offline/config/docs 검사를 다시 실행합니다.
  2. appstore:vX.Y.Z Linux/AMD64 image를 build합니다.
  3. appstore-vX.Y.Z.tar.gz를 만들고 gzip, manifest, version label과 non-root user를 검증합니다.
  4. 인터넷 egress가 없는 Docker network에서 PostgreSQL과 AppStore를 기동합니다.
  5. ready, version과 SPA response가 정상일 때 SHA-256을 release notes에 기록합니다.
  6. custom asset 한 개를 업로드하고 Release API에서 이름과 개수를 재검증합니다.
GitHub 제약: Release 화면에는 GitHub가 Source code (zip)과 Source code (tar.gz)를 자동으로 추가하며 제거할 수 없습니다. AppStore workflow가 업로드하는 custom asset은 서비스 image archive 한 개뿐입니다.

7. 게시 후 독립 검증

  1. Release API와 화면에서 tag, title, custom asset 이름·개수와 SHA-256을 확인합니다.
  2. CI workspace가 아닌 새 host로 asset을 내려받아 checksum을 비교합니다.
  3. 기존 local image를 사용하지 않도록 확인한 뒤 archive를 docker load합니다.
  4. OCI version·revision, non-root user와 architecture를 확인합니다.
  5. 외부 인터넷이 차단된 검증 network에서 오프라인 Acceptance를 실행합니다.
  6. 성공한 release URL, checksum, 검증자와 시각을 변경 기록에 남깁니다.

8. GitHub Pages 홍보·가이드 배포

.github/workflows/pages.yml은 main의 docs/** 변경에서 정적 파일, canonical·OG·JSON-LD와 screenshot manifest를 검사한 뒤 Pages artifact를 게시합니다.

  • 모든 CSS, JavaScript, SVG와 screenshot은 docs/ 안에 있어야 하며 CDN을 사용하지 않습니다.
  • sitemap.xml, robots.txt, llms.txt의 canonical host가 실제 Pages URL과 일치해야 합니다.
  • visible FAQ와 FAQ JSON-LD 답변은 사실과 동일해야 합니다.
  • 모바일 viewport, keyboard focus, reduced motion과 16px 본문 가독성을 확인합니다.
  • repository의 Pages Source를 GitHub Actions로 한 번 활성화해야 합니다.
