BACKUP & RESTORE

Database와 암호화 Key를 함께 복구 가능한 상태로 유지하기

AppStore의 앱, 사용자, 권한, 설정, 암호화된 OIDC·AI secret과 Audit Log는 PostgreSQL에 있습니다. 하지만 이를 복호화하는 ENCRYPTION_KEY는 database 밖에서 별도로 보호해야 합니다.

목차백업 대상RPO·RTODB 백업Key 보관복원 시험장애 복구검증 기록

1. 백업 대상과 제외 대상

대상방법중요성
PostgreSQL database조직 표준 snapshot + 정기 pg_dump앱·사용자·권한·설정·Audit 전체
ENCRYPTION_KEY승인된 secret vault/오프라인 복구 봉투암호화된 OIDC·AI secret 복원 필수
배포 env와 reverse proxy 설정구성 관리 저장소, secret 값은 별도 vault동일 network·TLS 구성 재현
릴리스 image archive와 checksum승인된 binary 보관소database schema와 맞는 binary 복구
Bootstrap password 원문백업 dump에 포함하지 않음, vault에서 관리복구 관리자 로그인

Container writable layer는 백업 대상이 아닙니다. AppStore는 read-only root filesystem으로 실행하고 영속 상태를 PostgreSQL에 둡니다.

2. RPO, RTO와 보존 정책

  • RPO: 허용 가능한 데이터 유실 시간을 기준으로 PostgreSQL snapshot·WAL 보관 주기를 정합니다.
  • RTO: 새 Docker host, database restore, image load, DNS·TLS 전환과 acceptance test 시간을 포함합니다.
  • 보존: 일·주·월별 세대를 분리하고 Audit Log의 조직 보존 의무보다 짧지 않게 합니다.
  • 불변성: 운영 계정 침해가 backup까지 삭제하지 못하도록 별도 계정·보관소와 immutability를 사용합니다.
  • 암호화: backup at rest와 전송 매체를 암호화하고 접근·복원 기록을 남깁니다.

3. PostgreSQL 논리 백업

조직의 physical backup을 기본으로 두고, release 전에는 이식 가능한 custom-format dump도 생성하는 것을 권장합니다.

backup_stamp="$(date -u +%Y%m%dT%H%M%SZ)"
backup_file="appstore-$backup_stamp.dump"

pg_dump \
  --format=custom \
  --no-owner \
  --no-privileges \
  --file="$backup_file" \
  "$POSTGRES_DSN"

pg_restore --list "$backup_file" >/dev/null
sha256sum "$backup_file" >"$backup_file.sha256"

command history나 CI log에 DSN을 직접 출력하지 않습니다. backup 파일 권한을 제한하고 checksum과 database server version, AppStore version, migration 목록을 복구 기록에 함께 남깁니다.

4. ENCRYPTION_KEY 보관

Database dump만으로는 완전한 복구가 아닙니다. OIDC Client Secret과 AI API Key는 ENCRYPTION_KEY로 인증 암호화되어 있어 원래 Key가 없으면 복호화할 수 없습니다.
  • Key 원문은 source, image, release asset, screenshot과 database에 넣지 않습니다.
  • 운영 host의 제한된 env 파일과 별도 secret vault에 최소 두 복구 사본을 둡니다.
  • database backup 접근자와 Key 접근자를 분리하고 복구 시 이중 승인을 적용합니다.
  • 복구 시험에서는 Key 원문을 출력하지 않고 OIDC·AI 연결 시험의 성공으로 일치 여부를 확인합니다.
  • Key가 유실된 경우 기존 secret 복원은 불가능합니다. 새 Key로 서비스를 시작하기 전에 영향 분석과 secret 재입력 계획을 승인받습니다.

5. 격리 환경 복원 시험

  1. 격리 PostgreSQL database를 만듭니다.
    production application이 연결할 수 없는 host와 credential을 사용합니다.
  2. dump를 복원합니다.
    createdb appstore_restore_test
pg_restore \
  --clean --if-exists --no-owner --no-privileges \
  --dbname="$RESTORE_POSTGRES_DSN" \
  appstore-20260901T080000Z.dump
  3. 짝이 맞는 AppStore image와 ENCRYPTION_KEY로 시작합니다.
    복원 전 version과 동일한 image를 먼저 사용합니다.
  4. ready와 version을 확인합니다.
    자동 migration이 예상하지 않은 변경을 만들지 않았는지 log와 schema_migrations를 확인합니다.
  5. 기능 복구를 확인합니다.
    앱 수, 사용자·역할, OIDC·AI 연결 시험, Key metadata와 Audit Log 기간을 비교합니다.
  6. 시험 자료를 폐기합니다.
    검증 결과는 보존하되 restore database와 임시 env는 승인 절차로 제거합니다.

6. 장애 복구 순서

  1. 장애 범위와 마지막 정상 backup 시각을 확정하고 쓰기 traffic을 차단합니다.
  2. 새 PostgreSQL에 snapshot 또는 dump를 복원합니다.
  3. 복원 시점에 대응하는 appstore:vX.Y.Z image를 load합니다.
  4. 별도 vault에서 원래 ENCRYPTION_KEY와 bootstrap credential을 승인받습니다.
  5. 새 POSTGRES_DSN으로 container를 시작하고 ready를 확인합니다.
  6. 공개 탐색, SSO, Admin, API Key, MCP, AI와 Audit를 검증합니다.
  7. DNS 또는 reverse proxy를 전환하고 사용자에게 데이터 복구 시점을 알립니다.

7. 복구 가능성 증거

각 시험마다 다음을 기록합니다.

  • backup 식별자, SHA-256, 생성·복원 시각
  • PostgreSQL과 AppStore version·commit
  • 복원 담당자와 승인자, 격리 환경
  • 복원된 row 수와 핵심 acceptance 결과
  • OIDC·AI secret을 노출하지 않은 연결 시험 결과
  • 실제 RPO·RTO와 개선 작업
권장 주기: backup 성공 알림만 확인하지 말고 조직의 RTO에 맞는 정기 restore drill을 수행하세요.
